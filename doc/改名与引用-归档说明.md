## 2. 核心设计

### 2.1 统一入向查询

- 后端：`search_incoming_refs` → `fetch_incoming_direct_rows` / `resolve_incoming_host_entries` / `host_ref_groups_from_db`
- 改名分析**不再**单独写一套 SQL；与 BOM 引用查询同源读 `bom_xref` 表
- 默认按 **basename** 全库查引用（假定 basename 在工作空间内唯一）；路径不一致的 XLink 也会列入待修正

### 2.2 传递闭包（间接宿主）

- 勾选「含间接宿主」时：子装配直接引用的零件，总装配等上层 FCStd 也出现在宿主列表
- **间接宿主本文件内可以没有**指向目标 basename 的 XLink；UI 展示 `via_chain` 上子装配的待修正项
- 勾选间接宿主并写回时：后端 `_expand_selected_for_indirect_apply` 沿 `via_chain` 展开到**实际含待修正 XLink 的直接宿主**再改盘
- UI **不再**出现「总装配经子装配间接引用，改名时无需修正此文件」类文案；间接宿主标为「间接 · 待修正」，并说明勾选后将写回子装配 XLink

### 2.3 改名分析命中规则

- 按 XLink `file` 属性末尾 **basename** 匹配 `old_basename`
- 可同时修正 **basename** 与 **相对路径**（`preferred_xlink_attr_for_target`）
- 预览时 `list_all_matches=True`：路径已正确的 XLink 标 `ok`，错误标 `pending`

### 2.4 写回后索引刷新（2026-05-30 修复）

此前问题：写回只改 FCStd 磁盘，`bom_xref` 与 `ref_hit` 未同步，导致「修正一次后再分析，待修正反而增多」。

现已修复：

1. **写回成功后**调用 `refresh_bom_xrefs_for_hosts`：从磁盘重读已修正宿主，局部更新 `bom_xref`
2. **改名记录**（`rename_log_id`）的分析快照：`replace_ref_hits_for_rename_scan` **整表替换**该记录下全部 `ref_hit`（不再只删 `pending` 导致 applied 累积）
3. 持久化时写入正确 **status**（`ok` / `pending` / `applied`）；前端 `hitNeedsFix` 以 `proposed ≠ matched` 为准，`ok` 不误报为待修正

## 3. API 一览

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| POST | `/api/rename/analyze` | 改名分析（可选 `rename_log_id` 或 `old_basename` + `new_basename`） |
| POST | `/api/rename/apply` | 写回勾选宿主的 XLink |
| GET | `/api/rename/logs` | 改名历史 |
| GET | `/api/bom-xrefs/incoming` | 入向引用查询（与改名分析同源） |
| GET | `/api/bom-xrefs/outgoing` | 出向引用 |
| POST | `/api/bom-xrefs/rebuild` | 全量重建引用表 |

## 7. 已知限制与后续

| 项 | 说明 |
| --- | --- |
| basename 唯一性 | 全库 basename 查询假定唯一；重名文件需人工指定路径或先整理工程 |
| 间接宿主写回 | 改的是链上**直接宿主** FCStd，不是总装配内虚构的 XLink |
| 全量重建 | 写回后仅刷新**已修正宿主**的边；若工程大规模变更，仍建议在 CAD 索引页全量「重建引用表」 |
| 讨论稿 | [改名与XLink引用修正-规划讨论.md](改名与XLink引用修正-规划讨论.md) 仍为讨论稿；Web P0 能力已部分实现，细节以本文与源码为准 |

## 8. 验证结论（用户确认）

- 改名分析写回后，待修正计数正确下降，不再出现修正一次后再分析反而增多的问题
- 「引用查询」页与改名分析入向结果一致
- 间接宿主展示与写回行为符合 FreeCAD「每条 XLink 均含相对路径、链上均需修正」的预期
