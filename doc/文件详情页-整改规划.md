# 文件详情页 — 整改规划

> [文档索引](文档索引.md) · 状态：**Phase A 已落地**（2026-05-30）

## 1. 问题

「属性回写」与「改名与引用」实为**对同一 FCStd 文件**的操作，却拆成两个 workbench Tab：

- 重复载入文件、重复树选择逻辑
- 底部「引用查询」与上方「改名分析」数据源相同、界面重复
- 第一步/第二步、toolbar、说明文字堆叠，主区域显得杂乱

---

## 2. 目标

**一个文件 → 一个 workbench Tab**（`contextKey = repo_rel_path`），页内 **三个子 Tab**，职责对等、耦合尽量小：

- **属性回写** — 原导航「属性回写」整页能力，现为子 Tab
- **引用** — 关系浏览与写回
- **改名** — 磁盘改名与分析写回

| 子 Tab | 职责 |
| --- | --- |
| **属性回写** | BOM 字段编辑、推荐、写入 Document.xml（原独立「属性回写」页） |
| **引用** | 自动展示入向/出向 table；修正 XLink、修正引用名 |
| **改名** | 磁盘重命名；分析写回（可选改名后跳转引用 Tab） |

顶层导航：

- **文件详情**（原「属性回写」入口）→ 打开 `file_detail` Tab
- **改名分析**（原「改名与引用」）→ 仅改名**历史**分析与写回；磁盘改名、当前文件写回在 **文件详情 · 改名** 子 Tab

## 3. 信息架构

```text
┌─ 8000.001-H-PX-所有零件预览.ASSY.FCStd ─────────────────┐
│ ./01-零件装配/... · 入向 3 · 出向 48                      │
├──────────────────────────────────────────────────────────┤
│  [ 属性回写 ]  [ 引用 ]  [ 改名 ]                         │
├──────────────────────────────────────────────────────────┤
│  （子 Tab 内容，共用同一 rel / preview / form）            │
└──────────────────────────────────────────────────────────┘
```

### 3.1 载入与子 Tab 策略

- **默认**：树点文件 / 从零件目录打开 → 一个 Tab，子 Tab 默认 **属性回写**
- **带意图打开**：`openFileDetailForRel(rel, { subTab: 'rename' })`（属性回写字段点「去改名」、改名后跳转引用）
- **不**为同一文件开多个 workbench Tab；子 Tab 按需切换（「需要时有子 Tab」）

### 3.2 引用 Tab

打开文件或切到「引用」时并行请求：

- `GET /api/bom-xrefs/incoming?rel=...`
- `GET /api/bom-xrefs/outgoing?rel=...`

双 table 展示；操作栏：**修正 XLink**、**修正引用名**（与改名 Tab 共用写回 API）。

### 3.3 改名 Tab

- 当前名 → 目标名 → **执行改名**
- 改名成功后刷新引用摘要，提示切到「引用」Tab 做写回
- 高级：**改名后自动修正引用**（Phase 2）
